# 四象限时间管理应用规格说明

本文档记录 `grill-me` 访谈中从第一轮到当前的全部问题、用户回答和对应设计结论。

## 1. 产品定位

这是一个名为 `Kairos`、支持 macOS、Windows、Linux 的单用户、离线优先四象限时间管理桌面应用。

当前正式技术方案：

- Electron
- TypeScript
- React
- Vite
- Zustand
- Tailwind CSS
- Zod
- pnpm
- electron-builder

## 2. 访谈记录与决策

### 1. 是否需要账号、同步或协作？

问题：这是纯个人、离线优先的任务管理工具，还是必须支持账号登录、多设备同步或多人协作？

回答：纯个人、离线优先。不需要帐号登录、多设备同步、多人协作。

决策：不设计账号体系、云端同步、后端服务、协作权限和同步冲突处理。数据全部保存在本机。

### 2. 是否支持重复任务和日历？

问题：任务是否需要支持重复任务、截止时间提醒，或者日历视图？

回答：需要支持重复任务、截止时间提醒。日历视图可以先不做。

决策：第一版实现重复任务和截止提醒，不实现日历视图。

### 3. 应用完全退出后是否提醒？

问题：当用户完全退出应用后，截止时间提醒还必须正常触发吗？

回答：完全退出后不触发。如果应用有后台运行或驻留系统托盘时提醒即可。

决策：不做独立后台服务或系统级定时任务。应用运行或驻留托盘时，由 Electron 主进程负责调度提醒。

### 4. 支持哪些系统版本和架构？

问题：首发需要支持哪些系统版本和 CPU 架构？

回答：macOS 13 之后、只支持 Apple Silicon；Windows 支持 10 和 11；Linux 支持 Debian 系统，尤其是 Ubuntu。

决策：后续确认的首发构建矩阵为：

| 平台 | 最低范围 | 架构 |
|---|---|---|
| macOS | macOS 13+ | arm64 |
| Windows | Windows 10/11 | x64 |
| Linux | Debian 系，尤其 Ubuntu | x64 |

不支持 Intel macOS、Windows ARM64 和 Linux ARM64。

### 5. 如何分发？

问题：首发准备通过什么方式分发？

回答：GitHub。

决策：使用 GitHub Releases 手动分发各平台安装包，不考虑应用商店专用能力。

### 6. 是否需要自动更新？

问题：第一版是否需要自动更新？

回答：不需要。

决策：第一版不引入 `electron-updater`。用户通过 GitHub Releases 手动下载安装新版本。

### 7. 是一个看板还是多个项目？

问题：第一版是只有一个全局四象限看板，还是支持多个项目/清单？

回答：只有 1 个全局四象限看板。

决策：不引入项目、清单、工作区或多看板概念。任务模型保持扁平。

### 8. 单个任务需要哪些字段？

问题：任务是否需要子任务、备注、标签、附件或链接？

回答：第一版只保留标题、截止时间、重复规则、重要/紧急状态和完成状态。

决策：第一版不实现子任务、备注、标签、附件和链接。

### 9. 重复任务何时生成下一次实例？

问题：重复任务完成后如何处理？

回答：完成当前实例后自动生成下一次任务。

决策：每次完成当前实例后生成下一次实例，而不是直接修改当前任务的截止时间。

### 10. 重复任务逾期后如何处理？

问题：重复任务到了截止时间但没有完成时，是否跳过本次？

回答：保留为逾期任务，同时按照重复规则生成下一次任务。

决策：逾期实例继续保留；重复规则仍继续生成后续实例，不覆盖或删除逾期实例。

### 11. 提醒时间有哪些选项？

问题：截止时间提醒需要哪些时间点？

回答：允许用户为每个任务自定义提醒时间，并提供现成选项：提前一天、提前一小时、提前30分钟、提前15分钟、到点提醒。

决策：每个任务独立配置提醒时间，内置以下选项：

- 不提醒
- 提前一天
- 提前一小时
- 提前30分钟
- 提前15分钟
- 到点提醒

### 12. 重复规则支持哪些形式？

问题：除了每天、每周、每月之外，是否需要工作日、每隔 N 天/周/月、指定星期几、结束日期或重复次数？

回答：需要“指定星期几”。

决策：重复规则必须支持按指定星期几重复。基础的一次性、每天、每月固定日期规则按第一版范围保留；更复杂的间隔规则暂不实现。

### 13. 是否需要重复结束条件？

问题：重复任务是否需要设置结束日期或重复次数？

回答：不需要。

决策：不设置结束日期和重复次数。重复任务默认无限重复，直到用户停止或删除重复规则。

### 14. 编辑/删除重复任务的作用范围？

问题：编辑或删除重复任务时，是否需要区分当前实例和整个重复序列？

回答：需要。

决策：编辑和删除操作支持作用于当前实例或整个重复序列。

### 15. 是否支持“当前及未来实例”？

问题：是否还需要“当前及未来实例”这种第三种作用范围？

回答：第一版只需要“当前实例”和“整个序列”两种范围。

决策：不实现“当前及未来实例”操作。

### 16. 象限内如何排序？

问题：同一象限内按截止时间自动排序，还是允许手动拖拽排序？

回答：按截止时间自动排序。

决策：同一象限内按截止时间自动排序，不保留手动排序字段。

### 17. 跨象限拖拽是否修改状态？

问题：把任务拖到另一个象限时，是否自动修改重要和紧急状态？

回答：需要。

决策：拖拽到目标象限时，自动同步修改 `important` 和 `urgent` 两个字段。

### 18. 截止时间是否必填？

问题：截止时间是必填，还是允许没有截止时间？

回答：必须填写。

决策：每个任务必须设置截止时间。

### 19. 截止时间是否精确到时分？

问题：截止时间是否必须精确到日期和具体时间？

回答：需要。

决策：截止时间使用精确到日期和时间的 `datetime`，例如 `2026-08-24 18:30`。

### 20. 一个任务可以设置几个提醒？

问题：一个任务是否可以同时设置多个提醒？

回答：选择一个提醒时间。

决策：一个任务最多设置一个提醒时间。

### 21. 是否可以不提醒？

问题：提醒时间是否可以设置为“不提醒”？

回答：可以设置不提醒。

决策：提醒字段支持 `none`。

### 22. 是否开机自动启动？

问题：是否需要支持开机自动启动并驻留系统托盘？

回答：需要。

决策：支持开机自动启动和系统托盘驻留。

### 23. 点击关闭按钮时如何处理？

问题：点击主窗口关闭按钮时，是隐藏窗口还是退出应用？

回答：隐藏窗口并继续驻留系统托盘。

决策：关闭窗口只隐藏主窗口，不结束 Electron 进程。通过托盘菜单提供正式退出入口。

### 24. 是否需要导入导出？

问题：是否需要提供任务数据的导出和导入功能？

回答：需要。

决策：实现本地数据导出和导入，支持用户备份和迁移。

### 25. 导出格式是什么？

问题：是否只需要完整备份用的 JSON，还是还需要 CSV？

回答：不需要 CSV。

决策：只支持带版本信息的完整 JSON 备份格式，不实现 CSV 导出。

### 26. 是否需要多语言？

问题：第一版只做中文，还是同时支持中文和英文？

回答：只需要中文，但是从代码结构上预留后续国际化能力。

决策：第一版界面只提供中文。文案集中管理，预留国际化资源结构。

### 27. 是否支持深色模式？

问题：是否支持浅色、深色和跟随系统三种主题？

回答：先固定只有浅色。

决策：第一版只使用浅色主题。Tailwind 颜色使用统一设计 token，方便后续加入深色模式。

### 28. 导入数据如何处理？

问题：导入 JSON 时，是覆盖当前数据、合并当前数据，还是让用户选择？

回答：将备份任务合并进当前数据。重复任务和任务 ID 冲突时需要提示。

决策：导入默认采用合并模式；冲突必须进入交互式处理流程。

### 29. 导入冲突有哪些处理方式？

问题：任务冲突时是否支持保留当前、导入覆盖、两者保留并生成新 ID，以及对全部冲突应用同一选择？

回答：是。

决策：冲突处理支持：

- 保留当前任务
- 使用导入任务覆盖当前任务
- 两者都保留，并为导入任务生成新 ID
- 对全部冲突应用同一选择

### 30. 删除是否需要确认和撤销？

问题：删除任务时是否需要二次确认，是否提供撤销删除？

回答：删除任务时需要二次确认。不提供“撤销删除”功能。

决策：删除操作需要二次确认；不实现撤销删除。

### 31. 完成任务放在哪里？

问题：任务完成后是否继续显示在原象限，还是移出并进入回收站？

回答：完成的任务从四象限中移除，放到“回收站”中，按时间排序，最新的时间排在前面。

决策：完成任务从四象限移出，进入回收站，按完成时间倒序排列。

### 32. 已完成任务是否可恢复？

问题：回收站中的已完成任务是否可以恢复？是否支持永久删除？

回答：已完成任务不可以恢复。回收站需要支持永久删除。

决策：回收站中的完成记录不可恢复，但可以永久删除。永久删除需要遵守删除确认规则。

### 33. 错过提醒是否补发？

问题：电脑关机、睡眠或应用未运行导致错过提醒时，重新启动后是否补发？

回答：只提醒未来时间，不补发历史提醒。

决策：应用重新启动后只调度未来提醒，不补发已错过的提醒。

### 34. 是否需要快速创建任务？

问题：是否需要主窗口按钮、全局快捷键或托盘快速添加任务？

回答：只提供主窗口内创建。

决策：第一版只在主窗口内创建任务，不实现全局快捷键和托盘快速添加。

### 35. 开机启动后是否打开窗口？

问题：开机自动启动后，是打开主窗口还是只驻留托盘？

回答：只驻留系统托盘，不自动打开主窗口。

决策：开机启动后隐藏主窗口，仅运行托盘和提醒服务。

### 36. Linux 提供什么安装包？

问题：Linux 首发提供 `.deb`，还是同时提供 AppImage？

回答：只提供 `.deb` 安装包。

决策：Linux 首发只发布 Debian/Ubuntu 适用的 `.deb`，不提供 AppImage。

### 37. Windows/Linux 支持哪些架构？

问题：Windows 和 Linux 是否只支持 x64？

回答：Windows 和 Linux 只支持 x64，macOS arm64。不支持 Windows ARM64、Linux ARM64 和 Intel macOS。

决策：发布矩阵固定为：

```text
macOS 13+     arm64
Windows 10/11 x64
Linux Debian   x64 (.deb)
```

### 38. 重复任务下一次实例继承什么？

问题：重复任务生成下一次实例时，是否继承象限、提醒、标题和重复规则？

回答：继承。

决策：下一次实例继承标题、象限、提醒设置和重复规则，仅更新实例 ID、创建时间、截止时间和完成状态。

### 39. 删除整个重复序列时如何处理？

问题：删除整个重复序列时，如何处理已生成的未完成和已完成实例？

回答：删除该序列所有未完成实例，已完成实例保留在回收站。

决策：删除整个序列时删除所有未完成实例；历史已完成实例不删除，继续保留在回收站。

### 40. 每月重复任务采用哪种规则？

问题：每月重复任务支持每月固定日期，还是支持每月第几个星期几？

回答：每月固定日期，例如每月15日。

决策：第一版每月重复使用固定日期，不支持“每月第几个星期几”。创建时禁止选择31日，避免目标月份不存在指定日期。

### 41. 每月固定日期不存在时如何处理？

问题：如果重复任务设置为每月31日，但某个月没有31日，应该如何处理？

回答：创建时禁止选择31日。

决策：每月重复日期的可选范围限制为1日至30日，不允许创建每月31日的规则。

### 42. 通知权限被拒绝时如何处理？

问题：如果用户拒绝了系统通知权限，应用应该如何处理？

回答：在应用内显示提示，并提供“重新请求权限”按钮。

决策：通知权限被拒绝时，在应用内显示提示和“重新请求权限”按钮；不自动修改任务的提醒设置。

### 43. 回收站如何永久删除？

问题：回收站永久删除任务时，是否需要二次确认？是否支持删除单个任务或清空整个回收站？

回答：不需要，并且只清空整个回收站。

决策：回收站只提供“清空整个回收站”操作，不支持单条永久删除；清空时不需要二次确认。该操作不可逆。

### 44. 时间使用哪个时区？

问题：任务的截止时间和提醒时间使用哪个时区？

回答：始终使用系统当前本地时区。

决策：截止时间和提醒时间始终使用系统当前本地时区，不单独保存任务时区。

### 45. 是否需要首次启动引导？

问题：第一次启动应用时是否需要显示简短引导，还是直接进入空白四象限主界面？

回答：需要显示简短引导。

决策：首次启动显示简短引导，介绍四个象限、创建任务方式和系统托盘行为。引导完成状态保存在本机；设置或帮助菜单提供重新查看入口。

### 46. 是否可以重新查看首次引导？

问题：首次引导完成后，是否需要在设置或帮助菜单中提供“重新查看引导”的入口？

回答：需要。

决策：在设置或帮助菜单中提供重新查看引导的入口。

### 47. GitHub Releases 安装包如何命名？

问题：GitHub Releases 的安装包是否采用统一的产品名、版本、平台和架构命名格式？

回答：不采用普通的统一格式。需要采用内核的命名，并且文件名长度要统一，不足的部分使用不影响语义的占位符补齐。应用名不使用 `quadrant-planner`，而使用类似代号或寓言的单个英文单词。

决策：安装包不再使用产品代号前缀，直接使用固定长度的平台/内核代号。发布文件名主体固定为10个字符，具体命名如下：

```text
ms-win-nt#
ap-mac-xnu
lf-lin-lnx
```

对应扩展名分别为 `.exe`、`.dmg` 和 `.deb`，三个完整文件名长度统一为14个字符。`#` 是 `ms-win-nt#` 中的固定占位字符。

应用本身仍使用独立的单个英文单词名称，不能使用 `quadrant-planner`；应用名称和安装包平台代号分开。

### 48. 固定平台/内核代号是什么？

问题：是否采用固定长度的平台/内核代号，并使用占位符补齐？

回答：采用以下命名：`ms-win-nt#`、`ap-mac-xnu`、`lf-lin-lnx`。

决策：以上三组代号为正式发布文件名主体，主体长度均为10个字符。

### 49. 系统时区变化后如何处理？

问题：如果系统时区发生变化，已有任务的截止时间应该保持本地时间，还是保持同一个绝对时间点？

回答：保持原来的本地时间。

决策：任务使用本地时间语义。系统时区变化后，任务保持原来的本地日期和时分，不按绝对时间点自动换算。

### 50. 应用显示名称是什么？

问题：应用是否使用一个有寓意的单个英文单词作为显示名称？

回答：`Kairos`。

决策：应用正式显示名称为 `Kairos`，表示恰当的时机。应用显示名称与安装包平台代号分开：

```text
Windows 安装包主体：ms-win-nt#
macOS 安装包主体：  ap-mac-xnu
Linux 安装包主体：   lf-lin-lnx
```

## 3. 数据模型初稿

```ts
type ReminderOffset =
  | "none"
  | "one-day"
  | "one-hour"
  | "thirty-minutes"
  | "fifteen-minutes"
  | "at-time";

type RecurrenceRule =
  | { type: "none" }
  | { type: "daily" }
  | { type: "weekly"; weekdays: number[] }
  | { type: "monthly" };

type TaskInstance = {
  id: string;
  seriesId?: string;
  title: string;
  important: boolean;
  urgent: boolean;
  dueAt: string;
  reminder: ReminderOffset;
  recurrence: RecurrenceRule;
  completed: boolean;
  completedAt?: string;
  createdAt: string;
  updatedAt: string;
};
```

说明：

- `seriesId` 用于关联同一重复任务序列。
- 象限由 `important` 和 `urgent` 计算。
- `dueAt` 必须包含日期和时间。
- 同一象限按 `dueAt` 升序排列。
- 已完成实例进入回收站，按 `completedAt` 降序排列。
- 不需要手动排序字段、备注、标签、附件或链接。

## 4. 进程与安全架构

```text
Electron
├── Main Process
│   ├── 窗口生命周期
│   ├── 系统托盘
│   ├── 开机启动
│   ├── 系统通知
│   ├── 提醒调度
│   ├── JSON 文件读写
│   └── 导入导出与冲突处理
├── Preload
│   └── contextBridge 安全 API
├── Renderer
│   └── React + Zustand + Tailwind CSS
└── Shared
    ├── TypeScript 类型
    ├── Zod schemas
    └── IPC contract
```

固定安全配置：

```ts
nodeIntegration: false
contextIsolation: true
sandbox: true
```

Renderer 不直接访问 Node.js 和文件系统，所有系统能力通过 Preload 暴露的最小化 API 使用。

## 5. 用户数据与备份

数据存储位置使用：

```ts
app.getPath("userData")
```

数据采用带 schema 版本的 JSON 文件。写入使用临时文件加原子替换，避免异常退出造成数据损坏。

导出：

- 导出完整 JSON 备份
- 不导出 CSV

导入：

- 默认与现有数据合并
- 任务 ID 或任务内容冲突时提示
- 可保留当前、导入覆盖、两者保留并生成新 ID
- 支持对全部冲突应用同一选择

## 6. 第一版功能范围

## 7. 发布与工程约束

GitHub Releases 发布以下安装包：

```text
macOS 13+     arm64
Windows 10/11 x64
Linux Debian   x64 .deb
```

第一版不使用 Electron 自动更新。业务代码和资源尽量控制在 1MB 内，但完整 Electron 安装包接受数十到上百 MB，因为 Electron 需要携带 Chromium 运行时。

包管理规范：

```text
包管理器：pnpm
锁文件：pnpm-lock.yaml
禁止混用 npm install
```
