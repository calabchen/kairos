# Kairos 验收 Checklist

本清单用于判断每个阶段、每个功能是否达到“合格”。

## 使用规则

- 每个条目只有在“合格标准”全部满足，并且“验证证据”已留下后，才能勾选。
- “实现”不等于“合格”：至少需要对应的自动化测试、手工验收记录或构建产物证据。
- 涉及时间、通知、托盘、开机启动和安装包的条目，需要在目标平台上验证；不能只以开发机通过为准。
- 正式产品范围以 `SPEC.md` 为准；`PLAN.md` 中与规格不一致的地方列在文末的 `$grill-me` 确认区。

## 验收状态

- [ ] 未开始
- [ ] 开发中
- [ ] 已实现，待验证
- [ ] 合格
- [ ] 阻塞 / 待确认

建议每项补充：实现版本、测试用例编号、验证平台、验证日期和证据链接。

## 阶段 0：工程基础与安全边界

### 0.1 项目可重复构建

- [ ] 使用 pnpm 管理依赖，并提交 `pnpm-lock.yaml`。
- [ ] `pnpm install --frozen-lockfile` 在干净环境成功。
- [ ] 开发启动、生产构建和测试命令已写入项目文档，且可重复执行。
- [ ] 未混用 `npm install` 生成或更新依赖锁文件。
- [ ] TypeScript 类型检查、Lint（如项目配置）和测试均能在 CI 或本地命令中运行。

合格标准：新环境按照文档操作即可完成安装、开发启动、构建和测试；不存在依赖锁文件漂移或必须依赖个人机器配置的问题。

验证：干净目录执行安装、类型检查、单元测试和生产构建，并保留命令输出。

### 0.2 Electron 安全配置

- [ ] 主窗口 `nodeIntegration: false`。
- [ ] 主窗口 `contextIsolation: true`。
- [ ] 主窗口 `sandbox: true`。
- [ ] Renderer 无法直接访问 Node.js、`require`、文件系统或 Electron 主进程 API。
- [ ] Renderer 需要的系统能力全部经 Preload 的最小化 API 调用。
- [ ] Preload 只暴露明确的白名单方法，不暴露原始 `ipcRenderer` 或任意 IPC 通道。
- [ ] IPC 输入在 Main 侧再次校验，不能信任 Renderer 传入的数据。

合格标准：安全配置固定符合规格；尝试从 Renderer 直接读文件、访问 Node API 或调用未授权 IPC 均失败，同时正常业务 API 仍可用。

验证：安全配置测试 + 开发者工具手工检查 + IPC 越权负向测试。

### 0.3 Shared 类型、Schema 和 IPC 契约

- [ ] Task/TaskInstance、提醒、重复规则、导入备份和冲突结果有共享 TypeScript 类型。
- [ ] Zod schema 能拒绝缺失标题、缺失 `dueAt`、非法布尔值、非法提醒值和非法重复规则。
- [ ] `dueAt` 强制包含日期和时间，并按系统本地时间语义处理。
- [ ] 象限只由 `important` 和 `urgent` 计算，不保存可导致不一致的独立象限字段。
- [ ] 已完成实例包含完成时间；未完成实例不能伪造完成时间状态。
- [ ] 数据文件和导出文件包含 schema 版本。

合格标准：Main、Preload、Renderer 对同一数据使用同一契约；非法数据无法进入状态层或持久化层。

验证：Schema 单元测试覆盖合法、缺字段、错误类型、未知枚举和边界日期。

## 阶段 1：主窗口与四象限任务看板

### 1.1 应用启动和主窗口

- [ ] 应用显示名称为 `Kairos`。
- [ ] 首次启动可以进入简短引导；引导介绍四个象限、创建任务方式和托盘行为。
- [ ] 引导完成状态保存到本机，重启后不重复弹出。
- [ ] 设置或帮助菜单可以重新查看引导。
- [ ] 非首次启动直接进入主界面（除非用户主动重看引导）。
- [ ] 主界面为中文、浅色主题。
- [ ] 四个象限均有清晰名称和规则说明：立即处理、计划处理、尽快委托或处理、减少或删除。
- [ ] 看板只存在一个全局任务集合，不出现项目、清单或多看板切换概念。

合格标准：新用户首次启动能理解四象限并进入空看板；完成引导后重启行为正确；中文浅色主界面可正常使用。

验证：组件测试 + 首次启动/重启手工验收。

### 1.2 四象限展示

- [ ] 四个象限同时可见，任务按 `important`/`urgent` 的四种组合显示在正确象限。
- [ ] 未完成任务显示在四象限；已完成任务不再显示在四象限。
- [ ] 同一象限按截止时间 `dueAt` 升序排列。
- [ ] 无截止时间的任务不能通过 UI 创建或保存。
- [ ] 任务标题清晰显示，截止日期和具体时间可见。
- [ ] 逾期任务有明确的逾期视觉状态，但仍保留在所属象限。
- [ ] 空象限有可理解的空状态，不出现错误或布局塌陷。
- [ ] 长标题、窄窗口、较多任务时不遮挡操作控件，基本布局可用。

合格标准：任意任务的显示象限和顺序都与数据一致；截止时间必填且精确到时分；逾期不会被错误隐藏。

验证：React Testing Library + 包含四种象限、相同截止时间、逾期和长标题的手工验收。

### 1.3 新建任务

- [ ] 只能在主窗口内创建任务，不提供全局快捷键创建或托盘快速创建。
- [ ] 标题为必填，空标题不能提交。
- [ ] 截止日期和具体时间为必填，不能只填日期。
- [ ] 可选择重要/不重要和紧急/不紧急，默认值有明确且一致的行为。
- [ ] 可选择“不重复”、每天、指定星期几、每月固定日期。
- [ ] 每个任务可选择一个提醒：不提醒、提前一天、提前一小时、提前30分钟、提前15分钟、到点提醒。
- [ ] 新建后立即出现在计算出的象限中，并按截止时间排序。
- [ ] 新建任务持久化成功后，关闭并重新打开应用仍存在。

合格标准：合法表单创建出完整 TaskInstance；任何必填或非法输入均有中文提示且不产生脏数据。

验证：表单组件测试、Schema 测试、端到端创建并重启验证。

### 1.4 编辑任务

- [ ] 可以编辑标题、截止时间、重要/紧急状态、提醒和重复规则。
- [ ] 编辑后更新时间更新，任务不产生重复记录。
- [ ] 修改重要/紧急状态后任务移动到正确象限。
- [ ] 修改截止时间后所属象限内顺序立即更新。
- [ ] 编辑当前实例时只影响当前实例。
- [ ] 编辑整个序列时，对序列中未完成实例的影响符合产品定义，并不会删除历史已完成记录。
- [ ] 编辑流程不会意外改变已完成状态或完成时间。

合格标准：当前实例和整个序列两种操作范围均有明确提示，结果与用户选择一致；取消编辑不修改数据。

验证：单元测试覆盖单实例/序列编辑，E2E 验证提示、取消和重启后结果。

### 1.5 删除任务

- [ ] 删除未完成任务前显示二次确认。
- [ ] 取消确认不会删除任务。
- [ ] 确认后任务从当前看板和持久化数据中移除。
- [ ] 删除重复任务时可选择当前实例或整个序列。
- [ ] 删除整个序列时删除所有未完成实例。
- [ ] 删除整个序列时，已完成历史实例继续保留在回收站。
- [ ] 不提供撤销删除功能，界面不出现误导性撤销入口。

合格标准：任何未完成任务都不能被一次误点击直接删除；序列删除不误删已完成历史记录。

验证：确认/取消 E2E + 序列删除数据层测试。

### 1.6 完成与回收站

- [ ] 未完成任务可以标记完成。
- [ ] 完成时记录 `completedAt`，并从四象限移入回收站。
- [ ] 回收站按 `completedAt` 降序排列，最新完成的排在前面。
- [ ] 已完成任务不可恢复到四象限。
- [ ] 回收站只提供“清空整个回收站”，不提供单条永久删除。
- [ ] 清空回收站不需要二次确认，并明确这是不可逆操作。
- [ ] 取消完成（如 UI 保留该入口）必须遵守规格：不能把回收站记录恢复到四象限。
- [ ] 完成重复任务后按规则生成下一次未完成实例；当前完成实例仍在回收站。

合格标准：完成记录和活跃任务状态严格分离；重启后回收站内容、顺序和不可恢复约束保持不变。

验证：状态转换单元测试 + 回收站 E2E + 重启持久化测试。

## 阶段 2：任务移动、搜索与筛选

### 2.1 跨象限拖拽

- [ ] 未完成任务可从一个象限拖到另外三个象限。
- [ ] 拖到目标象限后自动同步 `important` 和 `urgent` 两个字段。
- [ ] 拖拽后任务显示在目标象限，并按截止时间重新排序。
- [ ] 拖拽失败或取消时，任务字段和位置不改变。
- [ ] 已完成任务不可从回收站拖回四象限。
- [ ] 键盘或无拖拽条件下仍有可用的编辑方式改变象限状态（如项目决定提供）。

合格标准：拖拽后的持久化数据与目标象限完全一致；刷新或重启后不会回到原象限。

验证：拖拽 E2E，覆盖四种象限、失败取消和重启后验证。

### 2.2 搜索

- [ ] 支持按任务标题搜索。
- [ ] 搜索结果只显示匹配任务，非匹配任务隐藏但不被删除。
- [ ] 搜索同时作用于四象限和回收站时，范围有清晰 UI 反馈。
- [ ] 清空搜索立即恢复完整列表。
- [ ] 无匹配结果显示中文空状态。
- [ ] 搜索不会修改持久化数据和任务排序字段。

合格标准：搜索是纯展示过滤，输入、清空、重启后数据均正确；大小写、前后空格和中文匹配行为固定并有测试覆盖。

验证：过滤函数单元测试 + 搜索 E2E。若大小写/空格行为尚未定义，先完成文末 `$grill-me` 确认。

### 2.3 基础筛选

- [ ] 至少支持按完成状态筛选。
- [ ] 至少支持按逾期状态筛选。
- [ ] 至少支持按提醒状态或重复状态筛选（若在界面提供）。
- [ ] 搜索和多个筛选条件同时使用时，组合逻辑明确且稳定。
- [ ] 清除筛选后恢复完整列表。

合格标准：筛选只改变展示，不改变任务；没有把已完成任务错误地重新显示为活跃任务。

验证：筛选组合单元测试 + E2E。

## 阶段 3：重复任务与时间规则

### 3.1 重复规则创建和校验

- [ ] 支持一次性任务。
- [ ] 支持每天重复。
- [ ] 支持每周指定一个或多个星期几。
- [ ] 支持每月固定日期。
- [ ] 每月日期只能选择1日至30日，不能创建31日规则。
- [ ] 不提供重复结束日期或重复次数。
- [ ] 重复任务默认无限重复，直到用户停止或删除重复规则。
- [ ] 每个重复实例都有唯一实例 ID，并通过 `seriesId` 关联同一序列。

合格标准：所有支持的规则能被创建、保存、重新编辑和正确展示；不支持的间隔规则、每月第几个星期几规则不能被伪造写入。

验证：重复规则 Schema 和日期计算单元测试，覆盖闰年、月末、跨年和指定星期几组合。

### 3.2 下一实例生成

- [ ] 完成当前重复实例后自动生成下一次未完成实例。
- [ ] 下一实例继承标题、象限、提醒设置和重复规则。
- [ ] 下一实例只更新实例 ID、创建时间、截止时间和完成状态等实例字段。
- [ ] 完成当前实例后，当前实例进入回收站，不被覆盖。
- [ ] 每月规则按固定日期生成，不生成不存在的31日实例。
- [ ] 每周规则按所选星期几计算下一次截止时间。
- [ ] 日期计算使用系统当前本地时区。

合格标准：重复完成不会丢历史，不会生成重复的同一实例；重启后序列关系、下一截止时间和继承字段正确。

验证：时间计算单元测试 + 完成任务 E2E + 重启后数据检查。

### 3.3 逾期重复任务

- [ ] 逾期实例继续保留并标记逾期。
- [ ] 逾期不会覆盖、删除或自动标记完成该实例。
- [ ] 按重复规则生成后续实例，后续实例可独立完成或继续逾期。
- [ ] 不会因为应用重启而重复生成同一个后续实例。

合格标准：逾期历史实例和后续实例同时可追踪，序列状态不会因调度器重复运行而膨胀出重复数据。

验证：模拟时间推进、应用重启和重复调度的幂等性测试。

### 3.4 序列操作

- [ ] 编辑提供“当前实例”和“整个序列”两种范围。
- [ ] 删除提供“当前实例”和“整个序列”两种范围。
- [ ] 不提供“当前及未来实例”选项。
- [ ] 停止重复或删除重复规则后，已存在的未完成实例如何处理符合已确认规则，历史完成实例仍在回收站。

合格标准：范围选择不会误作用于另一范围；序列关联数据可审计。

## 阶段 4：提醒、通知与托盘驻留

### 4.1 提醒调度

- [ ] 每个任务最多一个提醒，或选择“不提醒”。
- [ ] 提前一天、提前一小时、提前30分钟、提前15分钟和到点提醒的触发时间计算正确。
- [ ] 只调度未来提醒；应用启动后不补发已经错过的提醒。
- [ ] 应用主窗口打开时可以提醒。
- [ ] 应用隐藏到系统托盘后仍可以提醒。
- [ ] 应用完全退出后不触发提醒。
- [ ] 任务完成、删除或提醒改为“不提醒”后，旧提醒被取消。
- [ ] 系统时区变化后任务保持原来的本地日期和时分语义，不按绝对时间自动换算。
- [ ] 调度过程重启后不会重复发送同一提醒。

合格标准：在指定平台上，所有提醒选项的误差和重复发送行为符合项目约定；历史提醒绝不在启动时补发。

验证：可控时钟/模拟调度单元测试 + 运行中、托盘、重启场景手工验证。

### 4.2 通知权限

- [ ] 首次需要通知时正确处理系统权限请求。
- [ ] 用户拒绝权限后，在应用内显示中文提示。
- [ ] 提示提供“重新请求权限”按钮。
- [ ] 重新请求不会自动修改任务的提醒设置。
- [ ] 权限恢复后，未来提醒可以正常发送。

合格标准：授权、拒绝、再次请求三种状态都不会造成崩溃、死循环或静默丢失配置。

验证：各平台权限状态手工测试；必要时用系统设置撤销再授权。

### 4.3 系统托盘和窗口生命周期

- [ ] 应用提供系统托盘图标和菜单。
- [ ] 点击关闭按钮只隐藏主窗口，不结束 Electron 进程。
- [ ] 从托盘菜单可以重新显示主窗口。
- [ ] 托盘菜单提供正式退出入口。
- [ ] 正式退出后主进程结束，不再触发提醒。
- [ ] 开机自动启动可配置或按规格启用。
- [ ] 开机启动后只驻留托盘，不自动打开主窗口。
- [ ] 托盘驻留期间数据保存和提醒调度继续正常。

合格标准：关闭窗口、显示窗口、托盘退出和开机启动四种生命周期行为可重复验证，且平台行为符合 macOS、Windows、Linux 差异。

验证：三平台手工验收 + 主进程生命周期测试。

## 阶段 5：本地持久化、导入与导出

### 5.1 JSON 本地持久化

- [ ] 数据保存到 `app.getPath("userData")` 下的应用数据文件。
- [ ] 数据文件带 schema 版本。
- [ ] 创建、编辑、删除、拖拽、完成、序列生成和清空回收站都会持久化。
- [ ] 应用重启后任务、回收站、序列关系、提醒和排序均保持一致。
- [ ] 写入采用临时文件加原子替换。
- [ ] 写入失败时保留原文件，并向用户显示可理解的错误。
- [ ] 文件不存在、为空、损坏或版本不支持时有明确恢复/报错行为，不导致主进程崩溃。
- [ ] 不引入 SQLite、后端服务或云同步。

合格标准：正常退出、异常写入和损坏文件场景下数据不会静默丢失；同一份数据可被 Schema 安全读取。

验证：持久化单元测试、重启 E2E、模拟写入失败/损坏文件测试。

### 5.2 JSON 导出

- [ ] 可以从主界面导出完整任务备份。
- [ ] 导出为带版本信息的 JSON。
- [ ] 导出包含活跃任务、已完成记录、序列关系和必要的提醒/重复字段。
- [ ] 不提供 CSV 导出。
- [ ] 导出失败时显示错误，不生成误导性的成功提示。

合格标准：导出的 JSON 可通过 Schema 校验，并能在另一份空数据中导入后还原任务语义。

验证：导出文件 Schema 校验 + 导出后导入闭环测试。

### 5.3 JSON 导入和冲突处理

- [ ] 导入默认采用与当前数据合并，不直接覆盖全部本地数据。
- [ ] 导入文件版本、结构和字段先校验，非法文件不会部分写入。
- [ ] 任务 ID 冲突时进入交互式处理。
- [ ] 任务内容冲突时进入交互式处理。
- [ ] 单个冲突支持：保留当前、导入覆盖、两者保留并为导入任务生成新 ID。
- [ ] 支持对全部冲突应用同一选择。
- [ ] 生成新 ID 后不破坏序列关联和实例唯一性。
- [ ] 用户取消导入或冲突处理时，当前数据不被修改。
- [ ] 导入完成后显示新增、覆盖、保留和跳过的结果统计。

合格标准：导入是可回滚的原子操作；任何冲突选择都能预测性地产生正确数据，不会产生重复 ID、孤儿序列或半导入状态。

验证：导入 Schema、冲突矩阵、取消/失败回滚和完整备份恢复 E2E。
